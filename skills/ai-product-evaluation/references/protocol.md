# 评测协议

## 定标准

每个维度记录 ID、用户结果、适用范围、pass/fail/uncertain/na 的锚点、严重程度和判定方法。先定义不能破坏的约束，再定义体验质量。阈值由产品负责人确认，未经确认写“建议”，不能因为样本恰好通过就事后下调。

建议根据任务选取：任务达成、事实与来源、上下文连续性、自主权与安全、表达清晰、差异化、端到端可靠性、成本与延迟。不强制每个项目都有全部维度。格式测试不替代以上语义维度。

质量评审用离散锚点：pass 为满足当前判据；fail 必须给可定位原文和违反的判据；uncertain 为证据不足/歧义；na 必须说明为何不适用。不要给无法复核的“人味 87 分”。必要时按维度另设 0–2 等级，先校准评审者再使用。

## 建评测集

案例至少有：稳定 ID、场景族、语言、来源类型及定位、固定输入、评价维度、期望行为、禁止越界和对照目的。多轮案例保留失败前的必要历史，不只复制最后一句。尽可能冻结角色/资料版本、背景、历史、顺序和生成参数；缺失记 unknown。

从真实失败建立开发案例，再补正常对照与近邻反例。例如“已明确保留下一决定”与“缺少必要信息、确实应当提问”必须分别评价，不能简单禁止所有问号。每个修改至少检查其目标失败与可能被误伤的能力。

留出集在按场景族拆分后保持不参与调优；同一案例换名字、翻译或近似改写不算独立留出。小样本先报告逐例结果；不得从方便样本推断总体通过率。涉及高风险边界仍需独立安全评审。

## 分析 Bad Case

记录如下内容即可，不要求每次写长报告：

1. 证据：case/run ID、原始输入和输出位置、最小必要原文。
2. 失败：违反哪个判据、用户受到什么影响、严重程度。
3. 原因：候选层、支持证据、反证、置信度；未验证写 hypothesis。
4. 验证：固定其余条件的最小实验及预期区分信号。
5. 修改：对应最小层、预计收益、成本及可能回归。
6. 结果：同输入前后证据、正常对照、剩余失败、保留/继续验证/撤回/延期。

原因层可选 data/context/prompt/orchestration/model/postprocess/ui/unknown。这是排查顺序，不是认定每个问题都出自 Prompt。若原始输出正确而显示错误，应检查后处理/UI，而不是继续堆模型规则。

## 做比较

比较同一版本案例和同一评审口径的前后结果。保留真实模型、Prompt/资料版本或哈希、温度、输入哈希、时间、重试和 token/耗时；不把请求成功当成质量成功。重复采样用独立 sample ID，不隐藏失败重试。

报告维度通过数/已评数、覆盖率、uncertain/na、缺失、运行错误以及关键失败。成本和耗时缺失不当作零。不只报均值，样本足够再讨论分位数。语义评审可让第二位人复核争议；若用模型评审，另行授权，冻结 rubric，隐藏版本标签、随机对调顺序并人工抽查偏差。模型评审不能独自证明原因。

停止条件：目标收益有证据且对照不退化则保留；改善不稳定或分歧较大则继续验证；伤害核心能力则撤回；收益不足抵消维护成本则延期。上线决定另受产品、安全和工程验收约束。

## 回流 MVP 与 demo

MVP 关注“最小功能范围仍交付完整价值”；评测关注“这个价值到底有没有发生”。把失败映射到核心假设，区分阻塞核心和可延期项。不是所有质量问题都需要新系统。

项目记录保留原始细节；通用 skill 只加入抽象且有适用条件的规则。新规则必须能改善目标案例、通过反例且不重复旧规则。没有跨场景证据时保留为项目策略，避免 skill 变成禁令仓库。
